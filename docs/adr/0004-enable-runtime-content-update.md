# 启用运行时内容更新闭环

现状是「远端包」只有本地开发服务器可加载：`DisableCatalogUpdateOnStartup = true`，且运行时不调用任何 `UpdateCatalogs`，所以远端 catalog 永远不会刷新，热更链路事实上不通。我们决定补齐闭环：启动流程显式执行「检查 catalog 更新 → 应用更新 → 计算远端依赖大小 → 按需下载（带进度）→ 进入游戏」，远端内容统一由 `Remote` 标签聚合。

「可远程热更内容而不用重新过审」是这套架构的首要目标；若客户端永不更新 catalog，则远端 bundle 的存在只带来风险而没有收益。选择「显式启动检查」而非「游戏内后台轮询」，是因为 bundle 与 catalog 更新需要冷启动语义，且在拿到玩家同意前不应消耗流量。

## Considered Options

- **保持现状（构建即发布，客户端不更新）**：实现最省，但违背首要目标，远端划分失去意义。
- **启动时静默更新**：实现简单，但玩家在不知情时等待下载，容易在弱网下卡启动。
- **显式检查 + 按需下载（采用）**：可展示大小与进度，可控。

## Consequences

- 冷启动引入一次 catalog 网络往返，以及可能的下载等待；需要失败与弱网回退路径。
- `Remote` 标签成为「所有需下载远端内容」的稳定载体，不能再随意增删。
- `OverridePlayerVersion`（原生版本）成为内容定位的一部分，发布时必须与远端目录一致。
- 需要与「构建/发布分离」分支一起设计，否则更新的内容无法安全地按版本回退。
